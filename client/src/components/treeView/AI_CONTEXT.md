# TreeView Client

Reusable TreeView state and Vue UI driven by a main-side `TreeViewDataProvider`.

## Structure

- `TreeView.ts` is the current Workspace aggregate and compatibility facade. It owns the selected Workspace identity, `isSelected` and layout metadata, complete Workspace record persistence, the replaceable `operations` surface, the controller, one shared remote DataProvider lifecycle, and the three feature models. Workspace records and snapshots natively contain Workspace-relative Tab paths and pass directly to and from the DataProvider without path-conversion wrappers. It never owns a Folder snapshot or a duplicate Tabs array.
- `workspace/TreeViewWorkspaceSelector.vue` and `treeViewWorkspaceSelectorModel.ts` own Workspace identity enumeration and selection UI. The model calls only `getWorkspaces`; TreeView reads selected Workspace contents and passes the current path back as a controlled value.
- `explorer/TreeViewExplorer.vue`, `treeViewExplorerModel.ts`, and `TreeViewNode.vue` own the Explorer UI, root and lazy Folder loading, ID/path indexes, selection projection, structural mutations, and the low-priority expanded-Folder restoration queue. The component observes TreeView's Workspace load revision and asks its model to load `workspacePath` as the root.
- `tabs/TreeViewTabArea.vue`, `treeViewTabsModel.ts`, `TreeViewTabs.vue`, `TreeViewTabPageHost.vue`, and `TreeViewSaveDraftDialog.vue` own Tabs state, Tab pages, menus, and Draft source operations. TreeView installs the Tabs snapshot already present in the Workspace record. TabsModel resolves relative paths against the Workspace directory in `install()` and returns relative paths from `getSnapshot()`, with `.` representing the Workspace root; live Tabs use absolute paths for entity access and UI consumers.
- `TreeView.vue` is the UI shell. It owns the sidebar container and expand/collapse controls, `SplitContainer`, sidebar width persistence, Workspace creation dialog, shared error toast, root ContextMenu area measurement, feature composition, and fact-event routing. New Workspaces and separator reset use the shared 400px sidebar default, while existing Workspace widths remain unchanged.
- Each model receives a `Pick<RemoteObject<TreeViewDataProvider>, ...>` contract for its own methods. All contracts adapt the same remote object; TreeView alone initializes and destroys it.
- TabArea requests integrity checks once per second without overlapping requests. TabsModel submits only its current Tab paths to the generic `checkEntitiesIntegrity()` API and ignores results from older Workspace installations or rebased paths. Confirmed missing targets switch mounted Tab pages to the existing invalid state, cancel pending page resolution, and unmount the business editor, discarding unsaved memory state. Tabs remain open; files are not recreated and invalid pages do not automatically reload when paths reappear.
- `treeView.controller.setStorageRoots()` validates replacement roots and reloads the Workspace aggregate through the existing Provider. Root changes do not recreate the models, Provider, or notifier.
- `TreeView.vue` owns the create-workspace dialog because Electron does not provide browser `window.prompt()`.
- Newly created Draft Items open directly as normal Tabs; they never enter the temporary preview state.
- `tabs/TreeViewSaveDraftDialog.vue` owns draft naming and selection among loaded target Folders. TabsModel moves and publishes the Item first; TreeView then synchronizes Explorer and the complete Workspace record without rollback, retry, or compensation. `controller.discardDraft()` remains the execution path after an outer close guard has already confirmed Don't Save.
- `explorer/TreeViewNode.vue` renders only expanded branches; collapsed descendants retain loaded model data without retaining Vue components or DOM. Folder layer reads have no temporary Loading row and reveal children directly when ready. Explorer selection gives the selected node a background. The active Tab path projection also emphasizes already loaded ancestor Folder text without loading or expanding missing branches.
- Explorer drag targets expose structural insertion feedback. A line above a row means a sibling insertion; a line below an expanded Folder occupies its first-child slot; an inside highlight appends to that Folder. The owner carries the displayed slot through to the target parent and `targetOrder`, including same-folder order-only moves.
- Ctrl/Meta-click adds or removes Explorer folders and items from a transient multi-selection. A multi-selection context menu exposes only Clone and Delete. Dragging any selected node moves the normalized top-level selection together; selected descendants are omitted when an ancestor folder is also selected.
- Opening a node context menu does not change the current Explorer selection or active Tab highlight. Folder and item menus first check only the target entity through `checkEntitiesIntegrity()`; an incomplete entity offers only Delete, while inspection errors are reported without opening a menu. Results are ignored when the workspace revision or target path changes. Menu actions target the node that opened the menu; when that node already belongs to a multi-selection, Clone and Delete retain their batch behavior.
- Clone and confirmed delete operations immediately use the application-level operation progress dialog. The renderer registers a Promise by operation UUID before starting each Main request, then keeps the dialog open until the DataNotifier resolves or rejects that operation after the queued filesystem work finishes. The dialog has no close or cancel action. Successful Workspace clone shows a toast that asks the user to switch Workspaces manually.
- `tabs/TreeViewTabs.vue` renders persisted Tabs directly from kind, ID, and path without requiring an Explorer entity. `tabs/TreeViewTabPageHost.vue` resolves the active entity through TabsModel, retains loading/ready/invalid state per persistent pane, and never merges the result into Explorer. Loading has no visible page; the persistent stack keeps the previous ready page displayed until the next business page is ready. A pane resolves once for its Tab ID; switching, preview promotion, parent rerenders, and path rebases preserve the mounted business page and its unsaved state. Closing the Tab removes the pane, so reopening resolves again.
- `treeViewDataNotifierRpcObject.ts` forwards main-side storage notifications to `treeView.controller.emitStorageChanged()` and non-fatal storage warnings to the application MessageStore.

## Boundaries

- Folder, Item, and Tab context menus provide their domain actions through the shared module-level `ContextMenu`, which composes externally positioned `PopupWindow`. TreeView passes its measured visible rectangle; Explorer and TabArea own anchors, targets, actions, and dismissal; ContextMenu owns body teleportation, final position calculation, area clamping, overflow scrolling, and menu styling.

- Folder, item, and tab overlay slots are absolute layers above complete default content. They do not replace TreeView-owned structure or behavior.
- Explorer rows, tabs, context menus, workspace creation, and draft saving use the compact visual language established by the reference TreeView without sharing its implementation.
- `isTabMultiline` is a business-owned presentation flag. Single-line tabs scroll horizontally; multiline tabs wrap through three visible rows and then scroll vertically.
- `isFolderTabVisible` and `isItemTabVisible` independently filter tab kinds. When both are false, TreeView hides the entire right workspace and renders a full-width Explorer-only layout.
- An open Tab page mounts on first activation and then stays mounted in the shared persistent stack; closing the Tab or switching Workspaces unmounts its page. A newly active page loads behind the previously displayed page and uses its slot readiness callback to replace that page only after reaching a stable loaded or unavailable state. Inactive pages remain measurable but cannot receive pointer, keyboard, or accessibility interaction. Persistent page keys include the absolute Workspace identity so equal entity IDs in different roots or Workspaces never reuse a page instance. `treeView.operations.switchTab` is the business override boundary for consumers that need additional cleanup or their own conditional page unloading when switching.
- TreeView snapshots and Vue components never retain or inspect business data. The entity-data API transports the nullable JSON `data` value together with ordered opaque extension entries; consumers own business serialization and preserve extensions they do not modify.
- Feature components invoke their owning model for unguarded source operations and publish typed facts to TreeView for downstream synchronization. Public and guarded workflows continue through `treeView.controller`; `treeView.operations` remains replaceable for business checks such as dirty Tab deletion and Workspace switching.
- Operations use the existing direct Promise queue. Explorer root and child reads additionally carry a load revision so stale same-Workspace reload results cannot overwrite newer state.
- TreeView UI never calls `BridgeRouter`. The model uses bridge factories only when it owns the generic DataProvider lifecycle; a consumer-provided DataProvider remains consumer-owned.
- TreeView never creates a Workspace implicitly. When storage has no Workspace, the content area presents a Create workspace action and hides the sidebar creation shortcut; the first manually created Workspace is selected and loaded immediately. When existing Workspaces have no selection, initialization selects and persists the first Workspace in selector order; multiple selected Workspaces remain an error.
- Deleting a Workspace requires confirmation through the application-level confirm dialog before the storage operation starts.
- Switching Workspaces loads the target Workspace record in TreeView, then updates `workspacePath`; the mounted Explorer loads only that root Folder layer. Creating or cloning a Workspace adds its ref without loading its tree; renaming rebases selected Explorer and Tab paths without rereading the root.
- TreeView creation operations do not accept or derive business defaults. Consumers interpret a new entity's `null` business data and persist concrete JSON through the entity-data API when needed.
- Explorer Item creation and Draft creation both use `Untitled` as the base name with numeric suffixes for existing names. Both first call the existing Provider proxy's `getAvailableItemPath()` and then pass that result to `createItem()`. The renderer does not inspect local files; a conflict arising after the name query remains a normal creation error without automatic renaming or retry.
- Folder and Item structural mutations update loaded branches and indexes without loading missing descendants. Moving an Item or Folder or saving a Draft rebases affected live Tab paths; Folder moves include Tabs for every descendant, and saved snapshots remain Workspace-relative. Workspace rename and clone preserve stored relative Tab paths unchanged; installing Tabs against the new Workspace directory supplies the new live paths. Application-initiated deletion closes matching path and descendant Tabs after storage succeeds, while external invalidation leaves unavailable Tabs visible.
- The Workspace selector stores the absolute Workspace path as its value. It displays only the Workspace name for one storage root, and `root key / Workspace name` when multiple roots require disambiguation.
- Breadcrumbs and business-facing source labels display paths relative to the Workspace parent, so the visible path starts with the Workspace name instead of exposing the absolute filesystem path. Breadcrumbs use the full Tab header width without per-segment truncation, scroll horizontally when needed, and disable text selection.
- Deleting the selected Workspace deletes it first, then selects the nearest remaining Workspace by selector position and loads only that Workspace. When none remains, the TreeView returns to its empty Workspace state.
