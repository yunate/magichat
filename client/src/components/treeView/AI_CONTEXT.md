# TreeView Client

Reusable TreeView state and Vue UI driven by a Backend-hosted `TreeViewDataProvider` over the direct Renderer-to-Backend connection.

## Structure

- `TreeView.ts` is the current Workspace aggregate and compatibility facade. It owns the selected Workspace identity, `isSelected` and layout metadata, complete Workspace record persistence, the replaceable `operations` surface, the controller, one shared remote DataProvider lifecycle, the business background queue and its lifecycle, and the three feature models. Command metadata work uses the generic `TaskQueue` in `common/taskQueue.ts`; Explorer loading does not use this queue. Background work starts automatically and does not pause with component mounting. Disposal first marks Explorer disposed and cancels its pending root publication, then cancels pending business work and awaits the current task before releasing an owned DataProvider. In-flight Folder RPCs are not transport-cancelled or awaited by disposal; successful late results are discarded. Explorer callers await `loadWorkspace()` or `loadFolder()` directly. Task failures use the queue's exception propagation behavior rather than a separate warn-and-continue wrapper. Workspace records and snapshots natively contain Workspace-relative Tab paths and pass directly to and from the DataProvider without path-conversion wrappers. It never owns a Folder snapshot or a duplicate Tabs array.
- `workspace/TreeViewWorkspaceSelector.vue` and `treeViewWorkspaceSelectorModel.ts` own Workspace identity enumeration and selection UI. The model calls only `getWorkspaces`; TreeView reads selected Workspace contents and passes the current path back as a controlled value.
- `explorer/TreeViewExplorer.vue`, `treeViewExplorerModel.ts`, and `TreeViewNode.vue` own the Explorer UI, root and lazy Folder loading, shared path queries, mutations, and expanded-Folder restoration. All entity actions, selection keys, and loaded-tree lookups use paths without an ID index or repair operation. `TreeView.selection` is a read-only computed projection of the active Tab path, passed to Explorer through its controlled `selectedPath` prop, including targets not loaded yet. ExplorerModel stores no selection state; transient multi-selection belongs to the view. Tab switches expand loaded ancestors. The view watches the selected path and root snapshots together and retains multi-selection that includes the target. A changed active path creates one pending reveal: once its virtual row exists, fully visible rows keep the current scroll position; offscreen rows move to one third of the viewport height, clamped at list boundaries. Completed reveals do not repeat on later tree publications or manual scrolling. Tree installations publish fresh shallow roots. `loadWorkspace(path)` resets Explorer context and the loaded-path set, then awaits `loadFolder(path)` when the path is non-null; null only clears the tree. `loadFolder(path)` reuses in-memory nodes for loaded paths and reads only unloaded paths from the DataProvider. Both cached and newly read nodes contribute expanded child paths to a LIFO stack for depth-first loading. Children are pushed in reverse order from a copied array, preserving the original sibling order and tree arrays; collapsed branches remain lazy. Each iteration yields through shared `sleep(0)`, while only newly read layers request a root snapshot publication. Workspace refresh clears the loaded-path set so contents are read again.
- `tabs/TreeViewTabArea.vue`, `treeViewTabsModel.ts`, `TreeViewTabs.vue`, `TreeViewTabPageHost.vue`, and `TreeViewSaveDraftDialog.vue` own Tabs state, pages, menus, and Draft operations. Tab identity is its path. TabsModel converts Tab paths, `activeTabPath`, and `previewTabPath` between relative persisted paths and absolute live paths, with `.` representing the Workspace root. Moves rebase descendants, active/preview state, and integrity results. Page cache keys exist only in a WeakMap, survive state cloning and path rebases, and never enter Tab records or RPC payloads.
- `TreeView.vue` is the UI shell. It owns the sidebar container and expand/collapse controls, `SplitContainer`, sidebar width persistence, Workspace creation dialog, shared error toast, root ContextMenu area measurement, feature composition, and fact-event routing. New Workspaces and separator reset use the shared 400px sidebar default, while existing Workspace widths remain unchanged.
- Each model receives a `Pick<RemoteObject<TreeViewDataProvider>, ...>` contract for its own methods. All contracts adapt the same remote object; TreeView alone initializes and destroys it.
- TabArea requests integrity checks once per second without overlapping requests. TabsModel submits only its current Tab paths to the generic `checkEntitiesIntegrity()` API and ignores results from older Workspace installations or rebased paths. Confirmed missing targets switch mounted Tab pages to the existing invalid state, cancel pending page resolution, and unmount the business editor, discarding unsaved memory state. Tabs remain open; files are not recreated and invalid pages do not automatically reload when paths reappear.
- Generic `treeView.controller.setStorageRoots()` validates replacement roots and reloads the Workspace aggregate through the existing Provider. The Command composition overrides this operation to recreate the complete TreeView, including its models, Provider, and notifier.
- `TreeView.vue` owns the create-workspace dialog because Electron does not provide browser `window.prompt()`.
- Newly created Draft Items open directly as normal Tabs; they never enter the temporary preview state.
- `tabs/TreeViewSaveDraftDialog.vue` owns draft naming and selection among loaded target Folders. TabsModel moves and publishes the Item first; TreeView then synchronizes Explorer and the complete Workspace record without rollback, retry, or compensation. `controller.discardDraft()` remains the execution path after an outer close guard has already confirmed Don't Save.
- Explorer flattens only expanded, loaded branches in Folder-before-Item order and omits Draft Items. `@tanstack/vue-virtual` mounts viewport rows plus eight overscan rows on either side in the existing scroll container, keyed by kind and path. Row elements are measured; 32px is only the initial estimate. `explorer/TreeViewNode.vue` renders one Folder or Item, not recursive children. Renaming and dragged rows stay mounted outside the viewport; rename targets scroll into view. Drag insertion indentation derives from logical depth, not mounted ancestors. Collapsed descendants retain loaded model data. Expanded unloaded Folders replace the caret with a loading indicator and reveal children as each layer finishes. Explorer selection gives the selected node a background; the selection path emphasizes loaded ancestor Folder text without loading or expanding missing branches. Ancestor highlighting follows each selected path toward the Workspace root with `dirname()` and checks only those Folder paths, without traversing unrelated subtrees. The root Folder stays excluded from ancestor emphasis.
- Explorer drag targets expose structural insertion feedback. A line above a row means a sibling insertion; a line below an expanded Folder occupies its first-child slot; an inside highlight appends to that Folder. The owner carries the displayed slot through to the target parent and `targetOrder`, including same-folder order-only moves.
- Explorer nodes activate and Folder carets toggle on left mouse press, without repeating on release. Name buttons and carets retain keyboard click activation; rename inputs, action buttons, and overlays do not activate the surrounding row on press. Double-click retains normal opening behavior. Ctrl/Meta-press adds or removes folders and items from a transient multi-selection. Pressing an already selected node preserves its group for dragging. A multi-selection context menu exposes only Clone and Delete. Dragging any selected node moves the normalized top-level selection together; selected descendants are omitted when an ancestor folder is also selected.
- Opening a node context menu does not change the current Explorer selection or active Tab highlight. Folder and item menus first check only the target entity through `checkEntitiesIntegrity()`; an incomplete entity offers only Delete, while inspection errors are reported without opening a menu. Results are ignored when the Workspace path or target path changes. Menu actions target the node that opened the menu; when that node already belongs to a multi-selection, Clone and Delete retain their batch behavior.
- Clone and confirmed delete operations use the application-level operation progress dialog's default 300ms delay, so faster operations complete without displaying it. The renderer directly awaits each DataProvider RPC Promise, keeping the dialog open until the queued filesystem work finishes or rejects. There is no separate operation ID or completion notifier. The dialog has no close or cancel action. Successful Workspace clone shows a toast that asks the user to switch Workspaces manually.
- `tabs/TreeViewTabs.vue` renders Tabs from kind and path without requiring an Explorer entity. TabPageHost resolves the active entity through TabsModel and retains loading/ready/invalid state without merging into Explorer. The persistent stack keeps the previous ready page displayed until the next page is ready. Switching, promotion, rerenders, and path rebases preserve mounted business pages. Closing a Tab or replacing a preview gives any subsequently opened page a fresh runtime cache key.
- `treeViewDataNotifierRpcObject.ts` forwards main-side storage notifications to `treeView.controller.emitStorageChanged()` and non-fatal storage warnings to the application MessageStore.

## Boundaries

- Installing a Workspace clears pending business background tasks before publishing the replacement state. This includes same-path refresh and empty Workspace installations. An already running task is not interrupted; consumers must reject stale results. Explorer `loadWorkspace()` itself does not cancel the business queue.
- Folder, Item, and Tab context menus provide their domain actions through the shared module-level `ContextMenu`, which composes externally positioned `PopupWindow`. TreeView passes its measured visible rectangle; Explorer and TabArea own anchors, targets, actions, and dismissal; ContextMenu owns body teleportation, final position calculation, area clamping, overflow scrolling, and menu styling.

- Folder, item, and tab overlay slots are absolute layers above complete default content. They do not replace TreeView-owned structure or behavior.
- Explorer rows, tabs, context menus, workspace creation, and draft saving use the compact visual language established by the reference TreeView without sharing its implementation.
- `isTabMultiline` is a business-owned presentation flag. Single-line tabs scroll horizontally; multiline tabs wrap through three visible rows and then scroll vertically.
- `isFolderTabVisible` and `isItemTabVisible` independently filter tab kinds. When both are false, TreeView hides the entire right workspace and renders a full-width Explorer-only layout.
- An open Tab page mounts on first activation and stays in the shared persistent stack. Closing it or installing another Workspace assigns new runtime keys and unmounts old pages, even if paths match. Workspace rename rebases live state without reinstalling Tabs, retaining existing pages. Newly active pages report readiness before replacing the previous display. Inactive pages remain measurable but cannot receive pointer, keyboard, or accessibility interaction. `treeView.operations.switchTab` remains the business override boundary.
- TreeView snapshots and Vue components never retain or inspect business data. The entity-data API transports the nullable JSON `data` value together with ordered opaque extension entries; consumers own business serialization and preserve extensions they do not modify.
- Feature components invoke their owning model for unguarded source operations and publish typed facts to TreeView for downstream synchronization. Explorer watches the existing selected Workspace ref, resets transient UI state, and invokes ExplorerModel's `loadWorkspace()`; that method delegates root loading to `loadFolder()`. Workspace enumeration replaces refs, so same-path refreshes still reload. A renamed Workspace whose loaded root has already been rebased does not reload. TreeView installs Workspace metadata without reading the Explorer tree or maintaining a revision counter; asynchronous workflow checks use the Workspace path. Explorer UI uses `loadFolder()` for expansion and creation preparation, and folder clone awaits it for expanded descendants. `loadFolder()` returns `Promise<void>`; consumers that need a Folder query the model after awaiting completion. TreeViewOperations and TreeViewController do not forward this primitive. Public and guarded workflows continue through `treeView.controller`; `treeView.operations` remains replaceable for business checks such as dirty Tab deletion and Workspace switching.
- Operations use the direct Promise queue. Explorer has a terminal disposed flag but no internal load revision or in-flight request map. Its load loop checks disposal before each iteration and after awaited Folder reads, preventing a discarded instance from reading descendants or applying late results. The loaded-path set avoids repeat DataProvider reads; cache hits still traverse expanded descendants. Missing cached nodes reject rather than silently reloading. Newly read paths are validated before publication. Loading assumes an active tree remains stable until completion; the Command owner handles Workspace and Root transitions by disposing and replacing the instance. Other concurrent creation, deletion, moves, and expand/collapse operations remain outside the loader contract. Directory read errors reject the complete load without retry, rollback, or automatic reload, retaining already published nodes. Mutations do not verify Workspace identity across awaits. Explicit resolution and inspection retain path traversal guards.
- Explorer stores a mutable tree. Metadata updates mutate loaded nodes in place. Folder reads replace the Workspace root or update a child entry through `TreeViewFolderUtils.UpdateFolder()`. Structural workflows call `TreeViewFolderUtils` directly and apply authoritative parent properties and ordering. `createFolder()` consumes the returned Folder snapshot without a second structural read. Folder clone inserts a distinct sibling path. Path-changing moves detach, rebase, and reinsert; same-path moves update ordering. Draft publication locates the source or already synchronized target by path, avoiding duplicate insertion. Filesystem operations remain with their owners.
- After storage deletion succeeds, parent metadata is read directly from the DataProvider. A failed parent read propagates without cached metadata fallback, rollback, retry, or automatic reload; the in-memory deletion is not applied at that point. Multi-step mutable updates are not transactional and do not restore earlier in-memory changes after a later failure.
- Explorer uses shared snapshot traversal for path lookups without separate entity indexes. The parameterless `_refreshRootFolder()` schedules one fixed 50ms timeout and skips scheduling while that timeout exists. Its callback reads the current root and publishes a shallow copy, without a separate pending-root field. Workspace clearing assigns null immediately; an outstanding callback reads the current state rather than restoring an older tree. Model operations can finish before the delayed reactive notification; tree mutations and RPC work are not delayed by this refresh timer.
- TreeView UI never calls `BridgeRouter`. The model uses bridge factories only when it owns the generic DataProvider lifecycle; a consumer-provided DataProvider remains consumer-owned.
- TreeView never creates a Workspace implicitly. When storage has no Workspace, the content area presents a Create workspace action and hides the sidebar creation shortcut; the first manually created Workspace is selected and loaded immediately. When existing Workspaces have no selection, initialization selects and persists the first Workspace in selector order; multiple selected Workspaces remain an error.
- Deleting a Workspace requires confirmation through the application-level confirm dialog before the storage operation starts.
- Switching Workspaces installs the target Workspace record and selected Workspace ref in TreeView. The mounted Explorer reacts to that ref and calls its model's `loadWorkspace()`, which resets context and awaits `loadFolder()` for the root and all expanded descendants. TreeView initialization, reload, and Workspace switching finish after metadata installation, not necessarily after Explorer loading; the model's loading Promise is the completion boundary for the expanded tree. Creating or cloning an unselected Workspace adds its ref without loading its tree; renaming rebases selected Explorer and Tab paths without rereading the root.
- TreeView creation operations do not accept or derive business defaults. Consumers interpret a new entity's `null` business data and persist concrete JSON through the entity-data API when needed.
- Explorer Item creation and Draft creation both use `Untitled` as the base name with numeric suffixes for existing names. Both first call the existing Provider proxy's `getAvailableItemPath()` and then pass that result to `createItem()`. The renderer does not inspect local files; a conflict arising after the name query remains a normal creation error without automatic renaming or retry.
- Structural mutations update loaded branches without loading missing descendants. Moves and Draft publication rebase live Tab paths while saved paths remain Workspace-relative. Workspace rename rebases existing Tabs without reinstalling them; clone preserves relative paths for later installation. Application deletion closes matching and descendant Tabs after storage succeeds, while external invalidation leaves unavailable Tabs visible.
- The Workspace selector stores the absolute Workspace path as its value. It displays only the Workspace name for one storage root, and `root key / Workspace name` when multiple roots require disambiguation.
- Breadcrumbs and business-facing source labels display paths relative to the Workspace parent, so the visible path starts with the Workspace name instead of exposing the absolute filesystem path. Breadcrumbs use the full Tab header width without per-segment truncation, scroll horizontally when needed, and disable text selection.
- Deleting the selected Workspace deletes it first, then selects the nearest remaining Workspace by selector position and loads only that Workspace. When none remains, the TreeView returns to its empty Workspace state.
