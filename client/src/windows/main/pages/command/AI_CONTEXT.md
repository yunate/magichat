# Command Page

The Command feature combines a workspace-level TreeView with one persistent `CommandTabPage` component instance per open Tab.

## Structure

- `CommandPage.vue` loads the active Root from Command settings, resolves its storage path through the Command storage RPC, and passes the root into TreeView. TreeView owns its generic DataProvider and notifier lifecycle. The page owns the separate Command storage proxy, its Main-to-Client push object, Workspace Env persistence, dirty-draft leave guards, before-app-quit callback implementation, Tab status overlays, and active-Tab Ctrl+S routing. It registers the Command Client immediately after obtaining the storage proxy, before TreeView and Item metadata loading, so CLI requests do not depend on that slower initialization work.
- Workspace switches, Root changes, refreshes, and selected-Workspace replacement recreate the complete TreeView through `recreateTreeView()`, rather than reusing its models or Provider. The page unmounts the old component, stops its Explorer loading and metadata watcher, performs the original selection or storage operation, disposes the old instance, and initializes a fresh instance with cleared page caches. Existing dirty-editor and running-command guards run before teardown. Creating or deleting an unselected Workspace retains the current instance and its open pages. Errors propagate and remain visible without automatically restoring an old instance or retrying initialization.
- The Command Page definition exposes a refresh action through a mounted lazy callback. Refresh applies dirty-editor and running-command guards, recreates the TreeView, and reports completion through MessageStore. Pages without a refresh callback hide the title-bar action.
- The Command Page definition also exposes a title-bar Environment action. `CommandEnvPanel.vue` uses the shared floating-window shell as a centered, movable, edge- and corner-resizable popup. It edits Workspace-owned Env groups through the shared parameter editor, and the group selected in its dropdown is the active runtime group. Its single close action persists the complete draft before closing.
- The Command Page definition registers `CommandHelpPanel.vue` for the shared title-bar Help action. The help page documents Root, Workspace, Folder, and Command creation, Macro scope priority, and language-specific `mhsetenv`, `mhgetenv`, and `mhcall` usage. It explains `mhgetenv` target scopes, exception conditions, valid empty values, and CMD nonzero exit codes.
- Initialization errors expose storage recovery actions: reveal the Command data directory, or explicitly confirm permanent deletion and recreate a clean default workspace.
- `CommandPage.vue` reads script types in the background as Explorer layers appear, without blocking loading or expansion. The selected Workspace ref identifies the cache lifetime: repeated business-data reads for the same ref preserve installed icons, while a replacement ref resets the cache even when its path is unchanged. Scheduling ignores mismatched root snapshots and skips paths already cached or attempted. Tasks check the current TreeView identity and captured Workspace ref before RPC and before applying results, then verify the Item path. The Command-owned cache is a shallow-reactive Map updated in place and cleared when recreating the TreeView. Item discovery still traverses the loaded tree. Invalid Item data logs a warning and retains the gray `UNK` icon without automatic retry. Open Tab state overrides this path-keyed cache.
- `CommandTabPage.vue` owns one entity's editor draft, TextEdit or Terminal component, save state, errors, dialogs, and Terminal placement. It defines the Command-only `mhsetenv` and `mhcall` completion snippets and supplies them through TextEdit's generic completion callback, including language selection and CMD `call` handling. Its Terminal toolbar presents the latest lifecycle or operation message in a compact live status area; errors also retain the application MessageStore notification. Folder editors own a complete square-cornered border. The shared `SplitContainer` owns the editor and Terminal split interaction without drawing item borders; the script editor and Terminal each own their own complete square-cornered border.
- `CommandTerminalMenu.vue` owns the Terminal toolbar overflow button, the Run as administrator checkbox, code view placement options, popup state, keyboard interaction, and menu styles. It binds Item placement and UAC through typed `v-model` values; the owning Tab page controls its draft, persistence, terminal lifecycle, and split layout. Direction keys navigate enabled menu controls; opening focuses the administrator checkbox when available or the selected placement while it is disabled.
- `CommandSettingsPanel.vue` exposes its current local `CommandConfig` and persists it on save. The framework passes that value to the optional boolean `beforeSaveCallback` before persistence and keeps settings open when it returns false. Command validates the proposed config and applies persisted defaults and Root changes in that callback.
- `commandSettings.ts` lazily loads and caches the complete `CommandConfig`, exposing only get and save operations. The settings controls edit a separate local copy.
- Command settings contain an ordered Root list with an immutable default Root first. Exactly one Root is active. The Command page reads the selected Root during initialization and applies proposed Root changes through its save-before callback.
- Changing the active Root reuses the workspace-switch guards: dirty editors require a save or discard decision, and running Commands require confirmation and are stopped before TreeView roots change. Cancelling either dialog rejects the settings save.
- `commandTabPageTypes.ts` defines the narrow registration contract used by the workspace to coordinate open Tab pages.
- Page registration, status overlays, and Folder caches use paths. A page exposes its current Tab path through a getter and re-registers the same API object after moves, transferring status to its new key. Leave guards retain page references across saves, so Draft publication still checks its running Terminal and closes its new path. Parameter-group IDs remain independent.
- `CommandPage.vue` directly owns the Command Client `call`, `getEnv`, and `setEnv` implementations. `CommandClientRpcObject` has no bridge dependency or constructor-side reference marking. The page explicitly marks it with `BridgeRouter.returnRemoteObj()` when passing it to storage `init()`, without an initialization helper. Its local helpers resolve CLI paths and selected parameter groups, read saved target Items and ancestor Folder data without loading Explorer branches, and share target persistence for default Workspace and explicit Macro updates.
- TreeView creates each `CommandTabPage` through its persistent `tabPage` slot on first activation. A page reports readiness after its business data loads or reaches its stable unavailable state, allowing the previous page to remain visible instead of exposing a transient loading frame. Tab switching keeps initialized pages mounted and measurable; closing the Tab unmounts only that page instance. Recreating the TreeView unmounts every old Tab page.

## State

- Each `CommandTabPage` loads business data on first activation, combining Item JSON metadata and the `script` extension. It owns its draft, saved baseline, and preserved extensions without an entity ID. Draft Items are always unsaved: Save persists and opens the publish dialog; Don't Save deletes the file after running-command guards pass. Parent-path changes refresh ancestor Macro scopes. Successful refreshes temporarily hide but do not unmount the editor or replace its draft and Terminal. Existing ancestor-load errors still expose the unavailable state.
- New TreeView entities expose `null` business data. Command initializes those editor drafts and ancestor scopes from its current serializer defaults, with a new Item's code view placement set to `follow`, without treating malformed non-null JSON as valid.
- Item titles are edited in the Command toolbar and committed as TreeView move operations on blur or Enter; Command business data remains title-free.
- Save waits for an in-flight title move before resolving the current Item path, preventing a rename from making the Save target stale.
- Workspace and Folder saves serialize typed business JSON in the renderer. Item saves store typed metadata in JSON and replace the `script` extension from the in-memory `content` field while preserving other extensions. Save failures keep the draft dirty and prevent the pending close or workspace switch.
- Optional code view placement belongs to each Item draft and its `.mh` JSON metadata. The view and dirty comparisons treat an absent value as `follow` without adding the field. The first menu option follows global `codeViewPlacement` directly and reactively without changing the draft. Explicit positions override global settings; changing the Item's selected option participates in dirty checks and the existing Save, Ctrl+S, and leave guards. Hidden code views retain their editor and Terminal instances, with Save and Run available in the Terminal toolbar.
- Optional `isUAC` belongs to the Item draft and JSON metadata. The checkbox and dirty comparisons interpret an absent value as `false` without adding it to old data. Changing the effective value participates in the existing Save, Ctrl+S, and leave guards; Item cloning and save snapshots preserve it.
- A preview Command Tab becomes a normal unpinned Tab after its editor draft changes, its title rename succeeds, or its Terminal PTY opens, preventing later preview activation from replacing active work without applying explicit Pin behavior.
- Command data load, save, and title rename failures are shown through the Tab page popup toast rather than resizing the editor with an inline error row. A load failure leaves a stable unavailable state after the popup closes.
- Saving an item Draft from the editor toolbar first persists its current business data, then opens the TreeView folder picker to publish it as a regular Command.
- The workspace-level Command page handles Ctrl+S and Meta+S at the window boundary and delegates saving to the active Tab page.
- Tab close and workspace switch operations are wrapped at the TreeView operations boundary. Application close reuses the same dirty-save and running-command decisions through the callback registered by the Command Page definition. Dirty drafts are resolved first, then running helper invocations are stopped or the operation is cancelled. Tab close additionally permits an explicit Skip that excludes running Tabs from the current close operation. Closing a Tab disposes its Terminal runtime and PTY.
- Dirty tabs render a dot through the TreeView tab overlay slot. Running Command items keep their Explorer and Tab script icons visible while two highlighted points continuously travel around each icon's stationary border.

## Macro scopes

- Folder tabs edit named local parameter groups without a TextArea and open with the parameter panel expanded. Item tabs edit named local parameter groups and script content and open with the parameter panel collapsed. The selected group is persisted with each entity and supplies its active local Macro scope.
- Parameter-group and interpreter selection use the shared PopupSelect rather than platform-native select popups.
- Each item page receives ancestor folder scopes from root to nearest parent for Macro resolution. Pages keep persisted ancestor snapshots and prefer live Folder drafts through a shallow-reactive open-Tab registry, so registering or removing a Folder page invalidates dependent Macro scopes. Successful Folder editor saves and CLI Folder updates refresh persisted snapshots in open descendant pages; unsaved Folder edits never replace these snapshots.
- Later ancestor scopes override earlier ancestors, the active entity's local parameters override Folder scopes, and enabled entries from the selected Workspace Env group have the final highest priority. Folder and Item TextEdit help displays this order from highest to lowest.
- CLI `set-env` accepts one or more key/value pairs and an optional Macro target. Without a target it updates the selected Workspace Env group. `.` and `./` identify the running Item, repeated `../` segments identify ancestor Folders, `__root__` identifies the current Workspace, and normal paths remain Workspace-relative. It validates the complete batch before applying it to the target entity's selected group in one persistence operation. After persistence, an open target Tab receives only the updated keys in its draft and the complete persisted group in its baseline, preserving unrelated unsaved edits; a Folder update also refreshes that scope in every open descendant Tab. Workspace Env panel drafts remain untouched and a later panel Save intentionally replaces the complete persisted Workspace Env data.
- CLI `get-env` follows the same target semantics as `set-env`, defaulting to the selected Workspace Env group rather than the running Item. It reads only the target's selected persisted group and resolves enabled Macro dependencies within that group. Missing target paths and missing or disabled keys return an empty string, indistinguishable from a saved empty value. Invalid path syntax, unavailable Workspaces, permission/storage failures, Macro dependency errors, and CLI/RPC failures remain errors. It accepts `--path=<path>` and `--path==<path>`. PowerShell, Node.js, and Python `mhgetenv` helpers decode the internal JSON string response; CMD prints the raw value.
- CLI `prepare` and `set-env` share one path resolver. `.` and `./` identify the running Item, and every other explicit relative path expands from that Item node, so `../name.mh` identifies a sibling and repeated `../` segments move through ancestor Folders. Absolute paths and Workspace-inclusive paths copied from TreeView retain their existing bases. `prepare` resolves only an Item in the selected Workspace, loads persisted Item and Folder data, applies the standard Folder, Item, and Workspace Env macro precedence, and returns a run request used to generate the originating Terminal's temporary script description. It does not execute unsaved editor drafts or switch Workspace.
- Closing the Env panel, including through its X button, Escape, Workspace switching, Root changes, refresh, deletion, or application close, persists its complete draft first. A save failure keeps the panel open and rejects the pending close operation.

## Terminal

- Each persistent `CommandTabPage` directly owns its lazy Terminal component. Opening a Tab does not create a PTY. Run and Open create the selected shell only when no PTY is active. Close destroys the active PTY and returns the toolbar to its Open state. The Run as administrator checkbox lives in the three-dot Terminal options menu and uses the Param enabled-checkbox styling. It reads and updates the Item's persisted `isUAC`, controls the next creation, and is disabled while a PTY is active without restarting an existing PTY.
- Command settings are validated by `common/config/command.ts` and persisted as `data/config/command.json`. They select the active storage Root, configure the initial path used by newly created Terminals, and choose the global code view position, with left as the default and `hide` hiding only the code view. Global and Item positions have identical semantics; the former global `terminalPlacement` field is not migrated or accepted. Items using `follow` or omitted placement react to these settings; explicit Item positions remain unchanged. The settings panel resolves the default Terminal path marker through the Command storage API and displays the actual absolute path. `SplitContainer` follows each Item's selected axis and supports pointer and keyboard resizing.
- Development builds expose a Terminal toolbar diagnostic that appends the current logical line to MessageStore with JSON escaping so whitespace and control characters remain observable.
- Every script type uses a main-generated temporary script. A page creates an execution-only UUID, also used as its stable editor-model identity, independently of the entity path; CLI preparation creates a fresh execution UUID per request. Unchanged content can reuse the page's temporary file while its Terminal lives. Entity paths never become temporary-script basenames; shell-specific helpers own interpreter dispatch.
- Terminal exposes readonly local `hasConnectedPty` lifecycle state for Open, Run preparation, error presentation, and script-type changes; these actions do not query remote PTY status. This state is separate from the prompt-based running heuristic. Every Command PTY is created with the Terminal's one-second status check and a handler that exclusively synchronizes the page running state throughout the PTY lifecycle, including manually entered commands; Command actions never set running state directly. Terminal owns the prompt heuristic and exposes `isTerminalRunning()` so Run preparation uses the same observed state without duplicating its pattern. Running state is emitted to the workspace for indicators and leave guards. Before Run writes a script invocation to an existing PTY, the page requires explicit confirmation when Terminal reports running input or work, then interrupts, clears, and continues.
- `CommandTabPage` owns Run, Clear, Open, Close, script-type confirmation, and PTY lifecycle composition. Close destroys the active PTY, including any running foreground command, and then exposes Open for creating a new Terminal. The toolbar Clear action records the Terminal's prompt-based running state before clearing and sends `cls` only as its final step when the shell was idle; running work receives no clear command. Terminal failures are reported once through the application MessageBar instead of rendering error rows inside the editor or Terminal. Changing to a different shell type while a PTY is active requires confirmation, then sends Ctrl+C when needed, destroys the PTY, and leaves the Terminal closed until Open is selected. The reusable Terminal owns only xterm.js and the primitive RPC operations.
- Terminal lifecycle operations call the application-level `runWithOperationProgress()` API directly. Its controller owns operation exclusivity, and its host presents operations exceeding 300ms; faster operations complete without visual interruption. Helper execution remains interactive and uses the separate Command running state.
- The shared application-level `ConfirmDialog` host uses the common floating-window shell while retaining its modal backdrop and focus behavior. The workspace and each Tab page await the typed `confirmDialog(options)` API without maintaining dialog visibility or resolver state.

## Current boundaries

- Command storage accepts only the current strict data schema and does not migrate empty legacy data. Invalid storage remains untouched until the user explicitly chooses the destructive recovery action.
