# TreeView Contracts

Generic TreeView models, Folder and Item snapshot operations, serializers, absolute storage-path validation, and object RPC contracts shared by renderer and main.

## Folder Operations

- `treeViewFolder.ts` exports `TreeViewFolderUtils` through the TreeView module entry. Its static queries return existing snapshot objects or `null` without reading storage, loading missing descendants, or modifying the tree.
- `TreeViewFolderUtils.GetFolder(rootFolder, path)` walks a normalized absolute path one direct Folder level at a time, matching each path segment against the child's `name`. Folder names are expected to match their path's final segment.
- `TreeViewFolderUtils.GetItem(rootFolder, path)` accepts a normalized absolute `.mh` path, resolves its parent through `GetFolder()`, and matches the filename without its `.mh` suffix against the parent's direct Item names. Non-`.mh` paths and missing parents or Items return `null`.
- `DeleteFolder(rootFolder, path)` and `DeleteItem(rootFolder, path)` remove an existing direct child from its parent. `AddFolder(rootFolder, folder)` and `AddItem(rootFolder, item)` append a new child only when its same-kind name is absent. `UpdateFolder(rootFolder, folder)` and `UpdateItem(rootFolder, item)` replace the complete existing entity at the same path, retaining its collection position; they do not rename, move, or merge descendants.
- All six mutation methods require the parent Folder to exist in the supplied mutable snapshot. They return `false` without mutation for missing parents or required targets, duplicate additions, or incompatible names/paths. Update and delete methods have no root-specific rejection; they rely on parent and target lookup. `AddFolder()` explicitly rejects the supplied root itself. Item paths must end in `.mh`, and entity names must match their path basename without the Item suffix.
- Successful mutations modify the parent collections in place. Folder additions/deletions update `folderOrder`; Item mutations maintain `itemOrder`, excluding Draft Items and appending a newly published name when needed. No parent directories or snapshot nodes are created implicitly. Callers own storage persistence, index maintenance, and reactive notifications.

## Boundaries

- Workspace, Folder, and Item snapshots contain only TreeView-owned structural metadata. Business `data` is excluded from structural loads.
- Folder, Item, and Tab identity is their path. Their declared metadata contains no entity ID, and no duplicate-ID indexing or repair exists. Folder and Item records may retain undeclared redundant fields under the permissive serializer policy, but those fields do not participate in identity.
- Workspace records and RPC payloads store normalized Workspace-relative Tab paths, with `.` representing the Workspace root. `activeTabPath` references an open Tab and nullable `previewTabPath` references the single unpinned temporary Tab. Strict validation requires unique paths, rejects absolute paths and traversal segments, and requires an active path when Tabs exist. TabsModel converts all three path fields between relative persisted paths and absolute live state; Main performs no conversion or legacy ID-to-path migration. Tabs resolve storage directly without depending on the loaded Explorer tree.
- `fromStoredValue()` is the tolerant storage-read boundary, separate from strict `validate()`, `fromValue()`, and serialization. Missing or invalid Workspace `tabs` becomes `[]`; missing or invalid active paths select the first valid Tab, or `null` when no Tabs remain. Invalid preview references become `null`. The Workspace read result includes `hasValidTabs` so storage cleanup cannot mistake invalid Tabs for an intentionally empty session. Missing or invalid Folder order arrays independently become `[]`. Other required metadata and JSON parsing remain strict; these reads do not modify their input.
- Workspace, Folder, and Item create operations persist `null` as the explicit uninitialized JSON business-data state and do not accept business data. Entity-data methods transport that nullable JSON string together with ordered opaque extension entries. Business clients own defaults, serialization, validation, and preservation of extensions they do not modify.
- `TreeViewDataProvider` is called by the renderer. `init()` receives a `TreeViewDataNotifierClientRpcApi` object passed by reference; `dispose()` releases that reference. Clone and delete return Promises that settle after the queued filesystem work finishes; failures propagate through the RPC result. The notifier is called by Main only for external storage changes and non-fatal storage warnings.
- `TreeViewDataProvider.getFolder(path, depth?)` returns the complete recursive subtree when depth is omitted and limits enumeration to the requested positive depth otherwise. `getFolderProperties()` exposes only Folder metadata.
- `createFolder()` and `createItem()` return newly created structural snapshots. Item creation accepts its complete ID-free structural properties.
- `getAvailableItemPath(itemPath)` returns an unused normalized absolute Item path based on physical directory occupancy without creating or reserving it. Creation remains separate: `createItem()` uses the exact supplied path and rejects a conflicting target.
- Workspace rename accepts a validated new name; the main-side provider derives the sibling target path from the normalized source Workspace path.
- `TreeViewStorageRoot` identifies each business-provided root by a display key and absolute path. `TreeViewWorkspaceRef` preserves that root identity when Workspace names overlap.
- Workspace and folder paths are normalized absolute paths. Item paths are normalized absolute `.mh` file paths. `.mh` files contain a leading strict JSON document and zero or more standalone `---MH:<key>---` extension sections.
- Storage operation target paths remain explicit normalized absolute paths; Tab entries inside Workspace property records are Workspace-relative. Storage-root selection and business storage actions remain outside the generic DataProvider contract.
