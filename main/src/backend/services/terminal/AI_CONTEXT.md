# Terminal Runtime

Backend-side owner of per-Command interactive Windows PTYs.

## Structure

- `terminalRuntimeService.ts` exports `gTerminalRuntimeService`, a global `TerminalRuntimeService` that directly implements `TerminalRuntimeServiceApi`. It owns PTY instances through `PtyApi`, Command script preparation, temporary files, and CLI routing. Service and Factory `create()` both return `Promise<PtyApi>`, keeping the concrete wrapper out of their public contracts. `create(options, callback)`, `run(terminalId, request)`, and `destroy(terminalId)` are registered directly on that owner. The service imports `gPtyFactory` statically; the factory computes paths only when accessed, so Broker service acquisition does not read uninitialized application paths or create native PTYs. For UAC sessions, Backend records the original Broker proxy and explicitly delegates normal destruction to the Broker runtime before releasing its proxy handle and Backend-owned resources. Runtime acquisition returns the cached promise immediately or initializes the Broker on a cache miss, including during destruction. Destruction can therefore start and elevate a new Broker after connection loss. The packaged native runtime still requires separate deployment validation. Backend registers one `UacBrokerService.onDisconnect()` handler that calls `TerminalRuntimeService.onUacBrokerDisconnect()`. Broker service stores only that handler and binds it when creating each peer, resetting its connection before invoking it. Callers own invocation ordering and explicitly request resource disposal.
- `common/terminal/terminalRpcApi.ts` is the single source for the shared `PtyApi`, `PtyCallbackApi`, and exit data contracts. `RpcPty` implements `PtyApi`; `Pty` implements node-pty's `IPty` as a local native wrapper. `PtyOptions.info` selects backend and Windows build metadata from `TerminalPtyState` through `Pick`; the Factory supplies that option during native creation. Local PTY operations can complete synchronously; bridge proxies expose asynchronous calls. `pty.ts` generates terminal identity before native creation, delegates the native metadata getters and operations, and exposes local `onData/onExit` subscriptions outside the shared RPC API. It has no `getInfo()` method. The local readonly `terminalId` remains available before initialization for CLI environment construction; `basicInfo` and `initialPath` provide creation metadata to the RPC adapter and Pool. Its `init` requires a factory-owned token. `initialPath` records creation-time configuration, not the shell's live directory. `cmdPty.ts` and `powerShellPty.ts` implement native creation.
- `rpcPty.ts` wraps a concrete `Pty` and binds its local `onData/onExit` subscriptions directly to constructor-supplied `PtyCallbackApi` methods. It assembles `TerminalPtyState` in `getInfo()` from the local PTY's native properties, terminal identity, and creation metadata. It stores no callback field, applies no notification error policy, and does not own remote-object destruction. Operations delegate directly without an internal queue. Exit and kill dispose only the wrapper's subscriptions, preserving independent observers. `kill()` closes the PTY without a Service disposal hook. `getInfo()` remains readable after process exit or kill on Windows because node-pty keeps the native metadata fields; callers use its `terminalId` for Service registration and cleanup. Callback replacement is not exposed. Service callback wrapping handles notification failures without converting exits to error-message callbacks. The renderer owns the existing unexpected-exit message. Each runtime stores one `TerminalCallback`; its closure retains the original remote reference and its `dispose()` releases that reference during destruction.
- `ptyFactory.ts` exports the process-level `gPtyFactory` instance and owns a `Map<TerminalType, PtyPool>` currently containing only a PowerShell pool. Setting the initial directory updates configured pools, and shutdown disposes them. Its asynchronous `create(options, callback)` reads the shell type from `options.terminalType`, acquires a raw PTY inline, passes the supplied `PtyCallbackApi` directly to `RpcPty`, and returns it. Acquisition resolves the initial path before taking from the requested type's pool; an absent pool or a `0` miss calls `_create()` with the requested dimensions, without an extra resize. Only pool hits are resized; a resize failure kills the claimed PTY and propagates the original error. The shared native-creation path recursively creates and verifies the directory and preserves path and system reason in preparation errors. Prewarming uses the same `_create()` path, while pool hits reuse the prepared process without another directory check. CMD is not prewarmed. Warm processes use 80 columns and 24 rows. The factory supplies CLI environments but does not wrap callbacks. Runtime owns notification policy, business resources, and explicit disposal without knowing about pools.
- `ptyPool.ts` owns one terminal type fixed at construction, with its own entries array, `TaskQueue`, initial directory, and lifecycle. Factory `_create()` and the Pool's creation callback return `Promise<Pty>` directly; `take()` returns the original `Pty` or `0`. Pool entries contain only the PTY and its exit subscription, without a separate creation-info payload. Constructor `maxCount` defaults to `1` and limits only that pool. `setInitialPath()` synchronously creates and validates the normalized directory before updating the pool, destroying unclaimed processes, and cancelling queued replenishment. Each queue schedules one creation per `setImmediate()` turn without running it in the acquiring caller's synchronous path. `_refillOne()` creates one process, binds its exit subscription, and inserts it into the pool; the scheduling layer checks lifecycle state and schedules remaining capacity. Directory changes and disposal clear unclaimed entries; no version counter is used. Taking an entry removes the pool's native exit subscription before handoff; claimed processes are never returned to the pool. A type's acquisition, creation failure, and disposal do not mutate another pool. Readiness markers, shell-ready waits, and output limits are not used.
- `PtyFactory.resolveInitialPath()` resolves configured initial paths for native creation, prewarming configuration, and Command settings. Its `temporaryDirectory` getter computes the shared `data/tmp/terminal` path from initialized application paths when needed; script preparation and cleanup use that getter rather than an eagerly evaluated module constant. `cmdPty.ts` and `powerShellPty.ts` statically import `node-pty`'s `spawn`; Backend and Broker runtimes must provide that dependency. Only `_create()` starts a native PTY.
- Factory acquisition, native creation, and Service creation use the shared `TerminalPtyOptions` directly. Its required boolean `isUAC` defaults to `false` in the serializer's authoritative default, and Client currently requests ordinary terminals with `isUAC: false`. `create()` routes UAC requests directly to `_createUAC()` before taking a local pool entry. `_createUAC()` obtains the cached Broker runtime, exports the supplied callback with `returnRemoteObj()`, and directly returns `runtime.create({ ...options, isUAC: false }, callback)` without another callback adapter or `RpcPty` wrapper. The bridge forwards the returned proxy to the renderer. The original options remain unchanged and ordinary requests retain local acquisition and pool reuse.
- `common/terminal/terminalRunRequest.ts` owns the run-request model and `terminalRunRequestSerializer`. Both `run()` and `prepareRun()` validate through that shared serializer before generating scripts; the Service has no separate request-validation helper.
- `common/terminal/terminalPtyOptions.ts` owns creation options and their serializer. Service `create()` uses `terminalPtyOptionsSerializer` for exact schema, shell type, numeric field types, nonblank initial path, and the UAC boolean. Client separately applies `terminalDimensionsSerializer` for dimension ranges; Backend does not reintroduce those range checks. Scalar argument checks and Factory path/filesystem behavior are not separate record serializers.

## Boundaries

- Pool lifecycle messages use the `[pty-pool]` scope through the existing console-to-file logger bridge. Only take hits and miss reasons, refill completion with count and duration, directory changes, refill failures, and unexpected prewarmed process exits are logged. Terminal output and process environments are not logged.
- The Service uses one global runtime registry keyed by terminal ID, not per-connection ownership. Bridge object handles remain connection-scoped, but Service `run` and CLI `prepareRun` resolve against the shared registry. Every PTY generates a fresh UUID before spawning, so `MAGICHAT_CLI_TERMINAL_ID` matches `getInfo().terminalId`. Explicit Service destruction removes the registry entry; process exit alone does not. Callers own process-lifecycle decisions. Each runner scopes `MAGICHAT_CLI_COMMAND_PATH` to its logical Item. Executables are selected from shared enum values; renderer input cannot provide executable paths.
- `Pty` listens to native data immediately after spawning. Each data event appends to an unlimited string buffer; when a business handler exists, the buffer is taken and cleared before invoking it. Without a handler, output remains buffered until `onData()` invokes the same data handler with an empty string to synchronously flush it. `onData()` stores one callback directly; a new registration replaces the previous callback, and disposal clears only a matching callback. Re-registering the same data callback does not create independent subscriptions. `onExit` delegates directly to node-pty without caching or replay. The pool removes exited unclaimed processes and requests replacement on the first exit or when at least three seconds have elapsed since the previous exit callback. Every exit updates that timestamp, including throttled exits; skipped replenishment is not retried on a timer. Cached data callbacks may run before registration returns its disposable.
- Backend starts prewarming after the CLI Bridge is ready and updates the pool's directory after successful Command configuration saves. The same flow stores the latest directory in `UacBrokerService` and synchronizes changes only to an existing Broker, without triggering elevation. Broker initialization applies that directory through `UacBrokerServerRpcApi.setTerminalInitialPath()`, starting its separate PowerShell pool; initialization-time directory changes use the latest value. Configuration synchronization and background creation errors are logged without rollback or automatic retry; an initial Broker setup error propagates. Pool misses remain normal on-demand creation, and a failed acquisition is reported rather than replaced by another process. Application shutdown first stops the pool, starts `TaskQueue.cancel()` to clear queued replenishment, closes unclaimed processes, and awaits that cancellation until the current turn completes. Normal Broker shutdown also awaits its own factory disposal before closing the connection. Pools do not track a separate running-task promise. Directory changes and in-task capacity cleanup initiate cancellation without awaiting it. Existing Runtime processes are disposed separately.
- Interactive PowerShell uses PSReadLine `SaveAtExit` history persistence and automatically imports `native-tools/cli-helper/powershell/MagicHat.psm1`. The module exposes `Invoke-MagicHatRun` to dispatch a validated script type and path, `mhcall` to prepare and synchronously invoke a Command by storage path, and `mhsetenv` to forward one or more environment updates.
- Every MagicHat CLI environment prepends `native-tools/cli-helper/cmd/` to `PATH`, exposing `mhcall.cmd`, `mhrun.cmd`, and `mhsetenv.cmd` to direct CMD PTYs and CMD child processes launched across languages. Interactive CMD uses the `CMD ` prompt prefix before its current-path prompt, matching PowerShell's visible `PS ` shell identification; interactive and batch callers use `call mhcall "<path>"`, `call mhcall("<path>")`, or `call mhsetenv` so control returns to the caller.
- MagicHat-launched Node.js scripts automatically preload the CommonJS helper through `NODE_OPTIONS`, exposing synchronous global `mhcall(path)` and `mhsetenv(updates, targetPath?)` functions backed by the same CLI protocol and fixed interpreter dispatch. When Node or Python `mhcall(path)` dispatches a PowerShell script, the fixed `Invoke-MagicHatPowerShellScript.ps1` entry point loads `MagicHat.psm1` before running the target so nested shell helpers remain available and installation paths with spaces remain intact. The Node module path remains available through `MAGICHAT_CLI_NODE_HELPER` for explicit imports.
- PowerShell, CMD, Node.js, and Python `mhcall` errors preserve the CLI Bridge preparation detail, including the requested Command path when its content is empty.
- MagicHat-launched Python scripts receive `native-tools/cli-helper/python/` at the front of `PYTHONPATH`; Python's standard `sitecustomize.py` startup hook exposes synchronous `mhcall(path)` and `mhsetenv(updates, target_path=None)` built-ins. Explicit imports remain available from `MagicHat.py`.
- Service and `RpcPty` operations execute directly without a backend FIFO queue; callers own operation ordering. Service `create()` validates the shell type, wraps the supplied `PtyCallbackApi` through `_createPtyCallback()`, passes that wrapper to the Factory, registers the returned `PtyApi` by its terminal ID, and returns a ready PTY proxy. Factory owns initial-path resolution, directory preparation, and callback binding. Client measures and validates dimensions before creation or resizing; Backend delegates them without a dimension validator. The Command default `${MAGICHAT_DATA}/tmp/terminal` resolves to the shared helper directory. Creation errors preserve the failed path and system reason for the Command Tab's status and alert. Service `destroy()` closes that PTY through the appropriate local or Broker runtime, releases the original notifier and temporary files, and removes its registry entry, including already-exited instances. `disposeAll()` uses the same cleanup path. Callers must order creation and disposal and keep the bridge usable while explicitly releasing callbacks. Normal sessions use system ConPTY rather than node-pty's bundled `conpty.dll`; node-pty 1.1.0 backend clearing is a no-op for system ConPTY and WinPTY, so xterm also clears locally.
- PTY data and exit callbacks are forwarded directly, with output unchanged. `run()` derives one stable temporary script from the validated Command Item UUID, rewrites it only when its content changes, and sends a fixed helper invocation with the script type, absolute temporary path, and logical Command path to the active shell. PowerShell dispatches through `Invoke-MagicHatRun`; CMD dispatches through `mhrun.cmd`. `prepareRun()` reuses the same generation path and returns `type|temporaryPath|commandPath` for `mhcall` without writing PTY input. A script matching the host shell runs directly, while other types use their fixed interpreter. PowerShell helper cleanup restores the parent Command path and controlled default prompt even if the script changed them or failed.
- `RpcPty` retains its constructor-supplied `Pty` as a readonly non-null reference, including after exit or kill. It does not expose a presence flag or infer native-process liveness from that reference. The renderer maintains local lifecycle state from creation, closure, and exit notifications. The Service validates registry membership, while native operation errors propagate. The runtime does not track individual run completion, infer shell prompt state, or parse PTY output; the renderer observes running work from the visible last line.
- Each temporary script uses the Command Item UUID as its stable base name and remains available while its PTY is owned. PTY disposal deletes its temporary files, and application shutdown clears the shared Terminal temporary directory.
- Service `_createPtyCallback()` handles asynchronous notifier failures by disabling further notifications and logging once without closing the PTY or retrying. Callback signatures use `PtyCallbackApi` and allow synchronous completion; synchronous callback exceptions propagate. On Broker disconnect, the Service traverses its UAC entries and calls their stored `callback.onExit({ exitCode: -1 })`, because the pipe cannot provide their actual exit codes. Each UAC wrapper shares one exit guard between normal exit and disconnect; ordinary terminals are not notified. There are no per-terminal disconnect subscriptions. Explicit Service disposal closes the PTY, destroys the original remote notifier, and removes the entry.
- Temporary-script deletion failures are logged.
