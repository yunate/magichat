# TreeView Storage

`LocalTreeViewDataProvider` is the generic filesystem implementation registered as `TreeViewDataProvider` in Backend, not Main.

## Boundaries

- The RPC registry returns the process-global `gLocalTreeViewDataProvider` for every remote-object request. Distinct proxy handles share one storage owner and queue. The service stores no business root; callers pass an absolute path for each operation.
- Resource reveals use `gBackendPlatform`, initialized once with Main's restricted Platform proxy. There is no per-Provider platform dependency or disposal callback. File reads, parsing, ordering, writes, cloning, and deletion all execute in Backend.
- `init(notifier)` retains the renderer's directly passed DataNotifier reference. The bridge binds the reverse proxy to the same peer; no notifier factory or register name is used. `dispose()` explicitly destroys the notifier reference.
- The singleton retains one active notifier. Repeated `init()` rejects rather than replacing another client's notifier. `dispose()` queues after pending mutations, destroys the current notifier, and allows a later explicit `init()` on the same instance. Backend normal shutdown calls this same `dispose()` before closing Renderer connections; no separate wait method or instance tracking is used.
- Command storage root authorization and explicit deletion/recreation are local Backend operations owned by `CommandStorageRpcObject`. There is no separate storage-root RPC or Main forwarding proxy.
- The DataNotifier connection remains owned by the provider, while current mutations do not emit `storageChanged()`.
- Mutating DataProvider operations and Workspace discovery run through one instance-local FIFO Promise queue. Pure metadata/entity reads and `getFolder()` execute independently, so active Tab reads do not wait behind background Explorer layer restoration. Workspace discovery remains queued because it removes orphan Drafts; init/dispose remain queued lifecycle mutations. `getFolder()` may synchronously persist reconciled order metadata as part of its atomic filesystem section, but it does not enter the background mutation queue. A rejected queued mutation does not block later mutations.
- Workspaces are directories. `__workspace__.mh` stores tabs, active and preview Tab paths, layout, and opaque consumer-owned `data`; every TreeView folder owns `__folder__.mh`, and items use `<name>.mh`. Tab paths, `activeTabPath`, and `previewTabPath` are Workspace-relative in records and RPC payloads. Backend reads/writes them unchanged; absolute-path conversion belongs to the renderer. Workspace structural reads exclude `data`, and property updates preserve it.
- Workspace, Folder, and Item creation writes `data: null`; creation RPCs do not accept business JSON. A later entity-data update replaces that explicit uninitialized value.
- `getAvailableItemPath()` is a separate read-only name query inside the operation queue. It checks all physical directory entries case-insensitively and adds ` 2`, ` 3`, and later suffixes before `.mh` until the name is unused, including paths occupied by invalid or unlisted files and directories. It does not create or reserve the returned path. `createItem()` uses exactly the supplied path and rejects an existing target without renaming or retrying. Existing entries are not modified or imported; move, rename, and save conflict behavior is unchanged.
- Workspace discovery skips Workspaces whose Workspace or root Folder metadata cannot be loaded and reports a full-path warning through the renderer DataNotifier. Storage reads tolerate missing or invalid Workspace Tabs/active/preview paths and Folder order arrays through `fromStoredValue()`, without automatically rewriting those invalid fields. Invalid active paths select the first valid Tab, or `null` when no Tabs remain. Other metadata and JSON parsing remain strict. Discovery deletes readable root Draft item files whose Workspace-relative paths are no longer referenced by valid persisted Tabs; when Tabs are invalid or missing, Draft cleanup is skipped. Invalid active/preview references alone do not disable cleanup. Unreadable Items remain untouched for normal tree loading to skip and report.
- Workspace rename accepts only a new name and derives the target beside the source directory, so the renderer cannot choose a different parent.
- Workspace, folder, item, and clone creation use `_runStagedCreate`: a stale stage is removed before creation, then all staged content is completed before one rename publishes the formal target. An existing formal target is never replaced.
- Clone and delete RPCs directly return `_enqueueMutation()`'s completion Promise, propagating original errors through the RPC result without a separate logging or error-conversion wrapper. Folder and Workspace clone use asynchronous file copies, while Folder and Workspace delete recursively remove entries through asynchronous filesystem calls. Both operations sleep for 3 ms after approximately 30 ms of traversal work, keeping Backend's event loop responsive without allowing another mutation to interleave. Clone publishing retries a staging-directory rename up to five times at 50 ms intervals only for transient `EPERM` or `EBUSY` errors. Other errors fail immediately; clone failure removes the staging directory, and cancellation is not supported.
- Workspace deletion only deletes the requested directory. The renderer selects or creates a replacement after the deletion succeeds.
- Folder and Item creation returns structural snapshots without generating entity IDs. No ID immutability checks or repair API exist. Item clone copies the complete source file byte-for-byte; Folder and Workspace clone recursively copy files without rewriting descendant metadata or expansion state. Workspace clone only resets `isSelected`; relative Tab paths need no rewrite. Successful clones still append the target name to parent ordering.
- Move requests include `targetOrder`. A same-path move updates only the parent `folderOrder` or `itemOrder`; a relocated entity is inserted at the requested position in its target parent.
- Folder and Item create, clone, move, and delete workflows maintain the owning Folder's order metadata. Move validates source and target order metadata before changing the source.
- Reading a folder reconciles `folderOrder` and `itemOrder` with its current children, removes missing entries, appends unordered children, and writes changed metadata only when both persisted order arrays were valid. Invalid order arrays use empty defaults for the in-memory reconciliation, without overwriting the original record during reads. Draft items remain excluded from `itemOrder`. `getFolder()` accepts an optional positive depth; omitted depth preserves full recursive reads, while the renderer uses depth `1` for Explorer layers and Tab Folder snapshots.
- Reading Folder properties is a lightweight metadata operation and does not traverse descendants or reconcile externally changed children.
- `checkEntitiesIntegrity()` checks only the entity paths supplied by the renderer and returns positional booleans. Items require a physical file; Folders require a directory and `__folder__.mh`; Workspaces additionally require `__workspace__.mh`. It does not scan directories, parse file contents, or repair resources. Inspection errors propagate rather than becoming missing results.
- Folder property updates preserve Server-owned order arrays after reconciling them with current children, so stale Client properties cannot overwrite structural ordering.
- Item updates keep the parent `itemOrder` synchronized with `isDraft`: Drafts are excluded, while regular items are present.
- Operations that require Workspace semantics discover the boundary from the absolute target path. Tree loading recognizes only child directories containing `__folder__.mh` and Item files ending in `.mh`. Missing markers, non-`.mh` files, links, and other unsupported entries are silently ignored so user resources can coexist with TreeView data. A recognized Folder or Item whose standard `.mh` metadata cannot be read or validated is skipped with a full-path warning through the renderer DataNotifier; the requested root Folder itself remains strict. Duplicate names within each child kind remain invalid, while a folder and an item may share the same name.
- Tree loads validate and return only TreeView-owned metadata. Workspace, Folder, and Item business data remains in the persisted record and is read or replaced as an unvalidated JSON string through the entity-data API.
