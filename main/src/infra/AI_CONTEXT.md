# Main Infrastructure

Local filesystem, configuration, JSON, log, and scheduling primitives. This module contains no business-domain decisions.

## Components

- `applicationPaths.ts` exports the global `gApplicationPaths` instance. It requires explicit `init(ApplicationPathsOptions)` and copies its configuration once; `getOptions()` returns an isolated copy for Broker initialization. The shared type and serializer live in `common/applicationPaths.ts`. Readonly getters derive application, renderer, preload, native-tool, external UAC Broker, and log paths without importing Electron or reading process-global paths. CLI environments use those same getters without maintaining separate path configuration. Reads before initialization and duplicate initialization throw. `appPath` is the repository during development and `resources/app.asar` when packaged; `appRoot` is `%LOCALAPPDATA%\MagicHat`. Logs use `appPath/log` during development and `appRoot/log` when packaged.
- `initializeApplicationPaths.ts` is Main's first imported module. It selects the development Electron profile when applicable, reads the authoritative Electron/process path values, and calls `gApplicationPaths.init()` before eager business-module path consumers run. Other Node entry points can import the owner directly and supply their own explicit configuration without loading this Electron initializer.
- `configManager.ts` directly implements `ConfigServerRpcApi`, derives and creates its config directory, maps Command, Task Center, and global config keys to filenames, and keeps shared serializers authoritative for domain conversion. Its local `onChange()` listeners receive the saved config key only after a successful atomic write; the returned callback unregisters the listener. Domain-specific reactions stay in the application composition layer.
- `jsonFile.ts` provides guarded JSON reads and atomic writes.
- `taskQueue.ts` automatically runs synchronous or asynchronous callbacks serially through browser-compatible `setTimeout()`, tracking the current turn with a completion promise. Main's PTY pool and renderer TreeView use the same TaskQueue class; there is no separate background queue or start/pause mode. Pending counts exclude the running task. Async `cancel()` immediately clears pending callbacks and waits only for the current scheduled or running turn, without interrupting its task or capturing task errors. Later enqueued work is outside that cancellation's wait. Async `dispose()` permanently ignores new work and awaits cancellation. A queued task must not await cancellation or disposal of its own queue. Callback rejections propagate while `finally` still schedules remaining work; the queue does not warn and consume failures.
- `mhFile.ts` owns TreeView's `.mh` container format. It stores one strict JSON document followed by standalone `---MH:<key>---` extension sections, applies last-value-wins semantics to duplicate keys, and writes through a unique sibling temporary file before rename. Rename retries use a 100ms monotonic-clock budget, including rename time, rather than a fixed attempt count. Each synchronous wait is at most 10ms and is capped by the remaining budget; no retry starts after the deadline. An in-progress synchronous filesystem call or delayed thread wakeup can exceed the budget because it cannot be interrupted. The temporary file is written only once; exhausted retries log the failure, use the existing temporary-file cleanup, and throw the last rename error. Temporary-file write failures are not retried.
- `logFile.ts` provides failure-tolerant task log append and read operations.
- `logger.ts` owns the process-wide `gLogger`, mirrors `console` output, serializes file writes, and creates one `mh-YYYY-MM-DD-HH-mm-ss.log` file per process start. It removes matching log files older than seven days in the background. Error objects are normalized to their name and message before file output, without the stack. `ScopeLogger` implements `Disposable` for paired start/end logging through `using`; `TimerLogger` uses the same pattern to emit elapsed milliseconds when its scope ends.
- `utils/pathUtil.ts` checks physical files and directories through Electron's unpatched `node:original-fs`, so paths containing an `app.asar` filename are not interpreted as virtual archive paths.

## Boundaries

- Keep Main's path-initializer side-effect import before business imports. Configuration and terminal modules derive some paths during module evaluation; initializing only in the entry module body would be too late. Main retains static business imports and top-level lifecycle functions.
- Business domains derive their own paths from `ApplicationPaths.dataDir`; global paths do not create business directories or write inside packaged `app.asar` resources.
- Application file logging is best effort. File setup or append failure disables file output for the process, reports through the original stderr, and leaves console output active without retrying or choosing another directory.
- JSON read from disk remains untrusted until the owning serializer or service validates it.
- Config RPC strings are validated through `common/config/configType.ts` before filename lookup or I/O. Unknown and inherited keys are rejected.
- Missing config files use fresh defaults. Invalid config files are logged and fall back to defaults.
- Task recovery uses structured silent reads so the service can report sanitized task locations instead of full filesystem paths.
- Atomic write failures preserve the previous file and remove temporary output.
