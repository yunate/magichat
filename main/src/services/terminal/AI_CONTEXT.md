# Terminal Runtime

Main-side owner of per-Command interactive Windows PTYs.

## Structure

- `terminalRuntimeService.ts` implements the instance-level `TerminalServerRpcApi`, owns one `node-pty` process, and pushes PTY output unchanged through `TerminalClientRpcApi`.
- `pty.ts` defines the abstract `Pty` wrapper, generates its readonly `terminalId` before constructing the process environment, records its creation-time `initialPath`, asynchronously creates the native process through an abstract `_create`, and delegates the complete `IPty` contract without caching its mutable properties. Its `init` requires a factory-owned TypeScript token; the factory initializes a PTY before exposing it. `initialPath` is not the shell's live working directory after commands such as `cd`. `cmdPty.ts` and `powerShellPty.ts` provide their executable and arguments and implement `_create`; CMD also configures its prompt environment when creating the process.
- `ptyFactory.ts` exports the process-level `gPtyFactory` instance and owns a `Map<TerminalType, PtyPool>` currently containing only a PowerShell pool. Setting the initial directory updates configured pools, and shutdown disposes them. Its asynchronous instance `create()` method uses the requested type's pool when present; an absent pool or a `0` miss creates a new process directly. CMD is not prewarmed. Warm processes use 80 columns and 24 rows and are resized to the caller's dimensions on acquisition. The factory supplies CLI environment callbacks and returns the initialized `Pty` plus backend/build metadata. The Runtime retains directory preparation, event subscriptions, process ownership, and disposal without knowing about the pools.
- `ptyPool.ts` owns one terminal type fixed at construction, with its own entries array, `TaskQueue`, initial directory, and lifecycle. Constructor `maxCount` defaults to `1` and limits only that pool. `setInitialPath()` synchronously creates and validates the normalized directory before updating the pool, destroying unclaimed processes, and cancelling queued replenishment. Each queue schedules one creation per `setImmediate()` turn without running it in the acquiring caller's synchronous path. `_refillOne()` creates one process, binds its exit subscription, and inserts it into the pool; the scheduling layer checks lifecycle state and schedules remaining capacity. Directory changes and disposal clear unclaimed entries; no version counter is used. Taking an entry removes the pool's native exit subscription before handoff; claimed processes are never returned to the pool. A type's acquisition, creation failure, and disposal do not mutate another pool. Readiness markers, shell-ready waits, and output limits are not used.
- `terminalRuntimeManager.ts` tracks Runtime instances independently of PTY creation for application shutdown, resolves CLI source routing against each Runtime's current PTY ID, and owns the shared `data/tmp/terminal` helper-script directory.

## Boundaries

- Pool lifecycle messages use the `[pty-pool]` scope through the existing console-to-file logger bridge. Only take hits and miss reasons, refill completion with count and duration, directory changes, refill failures, and unexpected prewarmed process exits are logged. Terminal output and process environments are not logged.
- Each RPC object is bound to its creating `BridgePeer`. Every PTY generates a fresh UUID and passes it to the injected environment callback before spawning, so `MAGICHAT_CLI_TERMINAL_ID` matches the returned `pty.terminalId`. CLI `prepare` resolves only the current PTY ID back to its Runtime; closing or reopening a PTY makes its old ID unavailable while the Runtime stays registered until disposal. Each runner scopes `MAGICHAT_CLI_COMMAND_PATH` to its logical Item so relative `mhcall` and `mhsetenv` operations remain correct across nested execution. Shell and interpreter executables are selected from shared enum values; renderer input cannot provide executable paths.
- `Pty` listens to native data immediately after spawning. Each data event appends to an unlimited string buffer; when a business handler exists, the buffer is taken and cleared before invoking it. Without a handler, output remains buffered until `onData()` invokes the same data handler with an empty string to synchronously flush it. `onData()` stores one callback directly; a new registration replaces the previous callback, and disposal clears only a matching callback. Re-registering the same data callback does not create independent subscriptions. `onExit` delegates directly to node-pty without caching or replay. The pool removes exited unclaimed processes and requests replacement on the first exit or when at least three seconds have elapsed since the previous exit callback. Every exit updates that timestamp, including throttled exits; skipped replenishment is not retried on a timer. Cached data callbacks may run before registration returns its disposable.
- Main starts prewarming after the CLI Bridge is ready and updates the pool's directory after successful Command configuration saves. Configuration and background creation errors are logged without automatic retry; pool misses remain normal on-demand creation, and a failed acquisition is reported rather than replaced by another process. Application shutdown first stops the pool, starts `TaskQueue.cancel()` to clear queued replenishment, closes unclaimed processes, and awaits that cancellation until the current turn completes. Pools do not track a separate running-task promise. Directory changes and in-task capacity cleanup initiate cancellation without awaiting it. Existing Runtime processes are disposed separately.
- Interactive PowerShell uses PSReadLine `SaveAtExit` history persistence and automatically imports `native-tools/cli-helper/powershell/MagicHat.psm1`. The module exposes `Invoke-MagicHatRun` to dispatch a validated script type and path, `mhcall` to prepare and synchronously invoke a Command by storage path, and `mhsetenv` to forward one or more environment updates.
- Every MagicHat CLI environment prepends `native-tools/cli-helper/cmd/` to `PATH`, exposing `mhcall.cmd`, `mhrun.cmd`, and `mhsetenv.cmd` to direct CMD PTYs and CMD child processes launched across languages. Interactive CMD uses the `CMD ` prompt prefix before its current-path prompt, matching PowerShell's visible `PS ` shell identification; interactive and batch callers use `call mhcall "<path>"`, `call mhcall("<path>")`, or `call mhsetenv` so control returns to the caller.
- MagicHat-launched Node.js scripts automatically preload the CommonJS helper through `NODE_OPTIONS`, exposing synchronous global `mhcall(path)` and `mhsetenv(updates, targetPath?)` functions backed by the same CLI protocol and fixed interpreter dispatch. When Node or Python `mhcall(path)` dispatches a PowerShell script, the fixed `Invoke-MagicHatPowerShellScript.ps1` entry point loads `MagicHat.psm1` before running the target so nested shell helpers remain available and installation paths with spaces remain intact. The Node module path remains available through `MAGICHAT_CLI_NODE_HELPER` for explicit imports.
- PowerShell, CMD, Node.js, and Python `mhcall` errors preserve the CLI Bridge preparation detail, including the requested Command path when its content is empty.
- MagicHat-launched Python scripts receive `native-tools/cli-helper/python/` at the front of `PYTHONPATH`; Python's standard `sitecustomize.py` startup hook exposes synchronous `mhcall(path)` and `mhsetenv(updates, target_path=None)` built-ins. Explicit imports remain available from `MagicHat.py`.
- Public RPC operations share one FIFO queue. `init()` idempotently connects the renderer notifier and never creates a PTY. `createPty()` atomically accepts the validated shell type, dimensions, and initial path and returns the actual Windows PTY backend plus OS build for xterm resize compatibility. The Command default `${MAGICHAT_DATA}/tmp/terminal` resolves to the manager-owned helper directory; every valid absolute initial path is recursively created when missing and then verified as a folder. Creation failures retain the failed path and system reason, while the Command Tab reports the same detail in its Terminal status and an alert dialog. `stop()` writes Ctrl+C without waiting for shell state, `clear()` requests node-pty buffer clearing without writing shell input, and `destroyPty()` closes the process. Normal sessions use the system ConPTY rather than node-pty's bundled `conpty.dll`; node-pty 1.1.0 defines backend clearing as a no-op for both system ConPTY and WinPTY, so renderer clearing remains local and resized PTYs may reprint prior content.
- PTY data and exit callbacks stay outside the operation queue. PTY output is forwarded unchanged. `run()` derives one stable temporary script from the validated Command Item UUID, rewrites it only when its content changes, and sends a fixed helper invocation with the script type, absolute temporary path, and logical Command path to the active shell. PowerShell dispatches through `Invoke-MagicHatRun`; CMD dispatches through `mhrun.cmd`. `prepareRun()` reuses the same generation path and returns `type|temporaryPath|commandPath` for `mhcall` without writing PTY input. A script matching the host shell runs directly, while other types use their fixed interpreter. PowerShell helper cleanup restores the parent Command path and controlled default prompt even if the script changed them or failed.
- The runtime exposes whether the PTY process is active. It does not track individual run completion, infer shell prompt state, or parse PTY output; the renderer owns completion detection from the visible last line.
- Each temporary script uses the Command Item UUID as its stable base name and remains available for reuse while the Terminal runtime is alive. Runtime disposal deletes files owned by that runtime, and application shutdown clears the shared Terminal temporary directory.
- Renderer notifier failure disables further notifications without closing the PTY. Peer disconnect, explicit disposal, or process shutdown still closes it.
- Temporary-script deletion failures are logged.
