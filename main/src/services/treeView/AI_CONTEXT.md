# TreeView Storage

`LocalTreeViewDataProvider` is the generic filesystem implementation registered directly as `TreeViewDataProvider`.

## Boundaries

- The RPC registry constructs it with a `BridgePeer`. The service stores no business root; callers pass an absolute path for each operation.
- `init()` creates and retains the renderer's DataNotifier remote proxy through the same peer.
- The DataNotifier connection remains owned by the provider, while current mutations do not emit `storageChanged()`.
- Mutating DataProvider operations and Workspace discovery run through one instance-local FIFO Promise queue. Pure metadata/entity reads and `getFolder()` execute independently, so active Tab reads do not wait behind background Explorer layer restoration. Workspace discovery remains queued because it removes orphan Drafts; init/dispose remain queued lifecycle mutations. `getFolder()` may synchronously persist reconciled order metadata as part of its atomic filesystem section, but it does not enter the background mutation queue. A rejected queued mutation does not block later mutations.
- Workspaces are directories. `__workspace__.mh` stores tabs, the temporary preview Tab ID, layout, and opaque consumer-owned `data`; every TreeView folder owns `__folder__.mh`, and items use `<name>.mh`. Tab paths are Workspace-relative in both persisted records and Workspace property RPC payloads. The provider validates and reads/writes them unchanged; absolute-path conversion belongs to the renderer. `.mh` content remains strict JSON. Workspace structural reads exclude `data`, and property updates preserve it.
- Workspace, Folder, and Item creation writes `data: null`; creation RPCs do not accept business JSON. A later entity-data update replaces that explicit uninitialized value.
- `getAvailableItemPath()` is a separate read-only name query inside the operation queue. It checks all physical directory entries case-insensitively and adds ` 2`, ` 3`, and later suffixes before `.mh` until the name is unused, including paths occupied by invalid or unlisted files and directories. It does not create or reserve the returned path. `createItem()` uses exactly the supplied path and rejects an existing target without renaming or retrying. Existing entries are not modified or imported; move, rename, and save conflict behavior is unchanged.
- Workspace discovery skips Workspaces whose Workspace or root Folder metadata cannot be loaded and reports a warning containing the full affected path through the renderer DataNotifier. It also deletes readable root Draft item files whose IDs are no longer referenced by persisted Tabs; an unreadable Item is left untouched for normal tree loading to skip and report.
- Workspace rename accepts only a new name and derives the target beside the source directory, so the renderer cannot choose a different parent.
- Workspace, folder, item, and clone creation use `_runStagedCreate`: a stale stage is removed before creation, then all staged content is completed before one rename publishes the formal target. An existing formal target is never replaced.
- Clone and delete RPCs validate a renderer-generated operation UUID, queue the mutation, and return immediately. Main reports final success or a sanitized failure through the renderer DataNotifier; detailed failures remain in the application log. Folder and Workspace clone use asynchronous file copies, while Folder and Workspace delete recursively remove entries through asynchronous filesystem calls. Both operations sleep for 3 ms after approximately 30 ms of traversal work, keeping the Electron Main event loop responsive without allowing another mutation to interleave. Clone publishing retries a staging-directory rename up to five times at 50 ms intervals only for transient `EPERM` or `EBUSY` errors. Other errors fail immediately; clone failure removes the staging directory, and cancellation is not supported.
- Workspace deletion only deletes the requested directory. The renderer selects or creates a replacement after the deletion succeeds.
- Tabs persist entity UUIDs, so rename and move do not rewrite tab identity. Folder and Workspace clone copy files without rewriting entity IDs or Folder expansion state. A cloned Folder merged into the selected tree receives new IDs through the renderer's duplicate-ID repair as each expanded layer is indexed. Workspace entity IDs remain scoped to that Workspace, and its relative Tab paths need no rewrite after copying.
- The renderer may request a duplicate entity ID repair while indexing a loaded tree. The provider rewrites only that entity's ID and reports a storage warning through the notifier if persistence fails.
- Move requests include `targetOrder`. A same-path move updates only the parent `folderOrder` or `itemOrder`; a relocated entity is inserted at the requested position in its target parent.
- Folder and Item create, clone, move, and delete workflows maintain the owning Folder's order metadata. Move validates source and target order metadata before changing the source.
- Reading a folder reconciles `folderOrder` and `itemOrder` with its current children, removes missing entries, appends unordered children, and writes changed metadata. Draft items remain excluded from `itemOrder`. `getFolder()` accepts an optional positive depth; omitted depth preserves full recursive reads, while the renderer uses depth `1` for Explorer layers and Tab Folder snapshots.
- Reading Folder properties is a lightweight metadata operation and does not traverse descendants or reconcile externally changed children.
- `checkEntitiesIntegrity()` checks only the entity paths supplied by the renderer and returns positional booleans. Items require a physical file; Folders require a directory and `__folder__.mh`; Workspaces additionally require `__workspace__.mh`. It does not scan directories, parse file contents, or repair resources. Inspection errors propagate rather than becoming missing results.
- Folder property updates preserve Server-owned order arrays after reconciling them with current children, so stale Client properties cannot overwrite structural ordering.
- Item updates keep the parent `itemOrder` synchronized with `isDraft`: Drafts are excluded, while regular items are present.
- Operations that require Workspace semantics discover the boundary from the absolute target path. Tree loading recognizes only child directories containing `__folder__.mh` and Item files ending in `.mh`. Missing markers, non-`.mh` files, links, and other unsupported entries are silently ignored so user resources can coexist with TreeView data. A recognized Folder or Item whose standard `.mh` metadata cannot be read or validated is skipped with a full-path warning through the renderer DataNotifier; the requested root Folder itself remains strict. Duplicate names within each child kind remain invalid, while a folder and an item may share the same name.
- Tree loads validate and return only TreeView-owned metadata. Workspace, Folder, and Item business data remains in the persisted record and is read or replaced as an unvalidated JSON string through the entity-data API.
